## Executive Summary

After a detailed review of Wally's current architecture — including conversation history management, system prompt construction, tool definitions, and the full request/response cycle — the assistant performs poorly not because the architecture is wrong, but because of five specific implementation gaps in the AI intelligence layer.

The foundation is solid. The tool-use loop, stateless backend, DB-persisted history, and intent-based knowledge injection are all correct patterns. These five fixes address what is actually causing the "clueless" behavior, ranked by impact.

| # | Fix | Impact | Effort | Priority |
|---|-----|--------|--------|----------|
| 1 | Structured Action Memory | Highest | Medium | P0 — Critical |
| 2 | Smart Tool Result Summarization | High | Medium | P0 — Critical |
| 3 | Context Budget Audit & Guardrails | High | Low | P1 — High |
| 4 | Model Routing (Default: Sonnet) | High | Low | P1 — High |
| 5 | Intent Classifier Improvement | Medium | High | P2 — Medium |

## Fix 1 — Structured Action Memory

**Impact:** Highest | **Effort:** Medium | **Priority:** P0 — Critical

### Problem

When a user says "undo what you just did" or "what plugins did you install?" the model has to reconstruct what happened by parsing raw conversation text. Tool results are large, verbose, and truncated at 4,000 characters before storage. The model frequently loses track of what it actually executed.

> **Root Cause:** The history stores conversation prose, not a structured record of actions taken. There is no dedicated memory of what the assistant did — only what it said.

### Solution

Add a dedicated action log that gets injected into the system prompt as a compact block. This is separate from conversation history and separate from the site profile. It answers the question: what has this assistant actually done in this session?

---

### 1.1 Action Log Schema (WordPress DB)

Create a new custom table to store structured action records:

```sql
CREATE TABLE wp_wally_action_log (
  id              BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  conversation_id BIGINT UNSIGNED NOT NULL,
  message_id      BIGINT UNSIGNED NOT NULL,
  tool_name       VARCHAR(100) NOT NULL,
  action_summary  TEXT NOT NULL,         -- human-readable, 1 sentence
  result_status   ENUM('success','failed','pending_confirm') DEFAULT 'success',
  key_params      JSON,                  -- only the most important params
  created_at      DATETIME DEFAULT CURRENT_TIMESTAMP,
  INDEX (conversation_id)
);
```

---

### 1.2 Populate on Every Tool Execution (PHP ToolExecutor)

After each successful tool execution, write a record to `wp_wally_action_log`. The `action_summary` must be generated by a small formatting function, not by the LLM:

```php
// class-tool-executor.php
private function log_action( $conversation_id, $message_id, $result, $tool ) {
    $summary = $this->format_action_summary( $tool['name'], $tool['params'], $result );
    global $wpdb;
    $wpdb->insert( $wpdb->prefix . 'wally_action_log', [
        'conversation_id' => $conversation_id,
        'message_id'      => $message_id,
        'tool_name'       => $tool['name'],
        'action_summary'  => $summary,
        'result_status'   => $result['success'] ? 'success' : 'failed',
        'key_params'      => json_encode( $this->extract_key_params( $tool ) ),
    ] );
}

// Format deterministically — no LLM call needed
private function format_action_summary( $name, $params, $result ) {
    $map = [
        'update_post'       => "Updated post #{$params['post_id']}: {$params['field']}",
        'install_plugin'    => "Installed plugin: {$params['slug']}",
        'activate_plugin'   => "Activated plugin: {$params['slug']}",
        'deactivate_plugin' => "Deactivated plugin: {$params['slug']}",
        'search_replace'    => "Search/replace '{$params['search']}' in {$params['scope']}",
        'trash_post'        => "Trashed post #{$params['post_id']}: {$params['title']}",
    ];
    return $map[$name] ?? "{$name} executed successfully";
}
```

### 1.3 Inject Action Memory into System Prompt (NestJS PromptBuilderService)

Fetch the last 15 action records for this conversation and inject them as a structured block in the system prompt, between Site Context and conversation history:

```typescript
// prompt-builder.service.ts
private buildActionMemoryBlock(actions: ActionLog[]): string {
  if (!actions.length) return '';
  const lines = actions.map(a =>
    `[${a.created_at}] ${a.result_status.toUpperCase()} — ${a.action_summary}`
  );
  return [
    '## Recent Actions Taken',
    'This is a structured log of actions you have executed in this conversation.',
    'Use this to answer questions like "what did you just do?" or "undo that".',
    '',
    ...lines
  ].join('\n');
}
```

**Expected output in system prompt:**

```
## Recent Actions Taken
[2026-03-08 14:32] SUCCESS — Installed plugin: yoast-seo
[2026-03-08 14:33] SUCCESS — Activated plugin: yoast-seo
[2026-03-08 14:35] SUCCESS — Updated post #42: title
```

### Acceptance Criteria

- [ ] Every tool execution writes a record to `wp_wally_action_log` within the same request cycle
- [ ] System prompt includes a `Recent Actions Taken` block on every request where actions exist
- [ ] Block contains at most the last 15 actions, formatted as single-line summaries
- [ ] Block adds no more than ~400 tokens to the system prompt
- [ ] Assistant can correctly answer "what plugins did you install?" without hallucinating

## Fix 2 — Smart Tool Result Summarization

**Impact:** High | **Effort:** Medium | **Priority:** P0 — Critical

### Problem

Tool results are stored raw in the database then hard-truncated at 4,000 characters. When a tool returns a large list of posts, plugins, or Elementor widget data, the stored version is a mid-sentence cut that looks like corrupted data to the model on the next retrieval.

> **Example:** A `list_plugins` call returns 8,000 characters of plugin data. The DB stores the first 4,000 characters. On the next message, the model reads a broken JSON fragment and either hallucates the missing plugins or claims it doesn't know what plugins are installed.

### Solution

Summarize tool results before storage, not after truncation. The summary is small, clean, and always complete. The raw result is never stored — only the summary. For the current tool-use loop iteration, the full result is still sent to the LLM; summarization only affects what gets persisted to history.

---

### 2.1 Summarizer Map (PHP)

Write deterministic summarizer functions for each tool type. No LLM call required for most tools:

```php
// class-result-summarizer.php
class Wally_Result_Summarizer {

  public static function summarize( string $tool_name, array $result ): string {
    switch ( $tool_name ) {

      case 'list_plugins':
        $count       = count( $result['plugins'] ?? [] );
        $active      = array_filter( $result['plugins'], fn($p) => $p['active'] );
        $count_active = count( $active );
        $names       = implode( ', ', array_column( array_slice($result['plugins'], 0, 5), 'name' ) );
        return "{$count} plugins found ({$count_active} active). First 5: {$names}.";

      case 'list_posts':
        $count  = count( $result['posts'] ?? [] );
        $titles = implode( ', ', array_column( array_slice($result['posts'], 0, 5), 'title' ) );
        return "{$count} posts returned. First 5: {$titles}.";

      case 'get_post_content':
        $words = str_word_count( $result['content'] ?? '' );
        return "Post #{$result['post_id']} '{$result['title']}' retrieved. {$words} words.";

      case 'search_replace':
        return "Search/replace completed: {$result['count']} replacements in {$result['scope']}.";

      case 'install_plugin':
        return "Plugin '{$result['name']}' installed successfully. Version: {$result['version']}.";

      default:
        // Fallback: JSON-encode, then truncate cleanly at a word boundary
        $json = json_encode( $result, JSON_PRETTY_PRINT );
        return strlen($json) > 800 ? substr($json, 0, 797) . '...' : $json;
    }
  }
}
```

---

### 2.2 Apply Summarization Before DB Write

In `class-rest-controller.php`, replace the current hard-truncation with the summarizer before writing the assistant message to the DB:

```php
// BEFORE (current behavior — remove this):
$content = substr( $tool_result_raw, 0, MAX_HISTORY_CONTENT );  // ❌ hard truncate

// AFTER (new behavior):
$content = Wally_Result_Summarizer::summarize( $tool_name, $tool_result );  // ✅ smart summary

// Then store $content in wp_wally_messages as normal
```

---

### 2.3 Preserve Full Result for Current Loop Iteration

The summarization only applies to what gets stored in history. Within the current tool-use loop (up to 10 iterations), the full tool result is still passed back to the LLM as a `tool_result` message. Only when the conversation ends and results are persisted does the summary replace the raw content.

| | Before (Current) | After (Fixed) |
|---|---|---|
| Stored in DB | 4,000-char hard cut of raw JSON — may be broken mid-record | Clean 1–3 sentence summary, always complete |
| Token cost in history | ~1,000 tokens per tool result | ~50 tokens per tool result |
| Model comprehension | Confused by broken/truncated data | Clear understanding of what happened |
| Current-loop accuracy | Full result (unchanged) | Full result (unchanged) |

### Acceptance Criteria

- [ ] Every tool result is summarized before DB write using the summarizer map
- [ ] No tool result stored in history exceeds 300 characters
- [ ] The current tool-use loop still receives full raw results (not summaries)
- [ ] `list_plugins` summary correctly reflects plugin count and names
- [ ] Default fallback never stores broken/mid-sentence JSON

## Fix 3 — Context Budget Audit & Guardrails

**Impact:** High | **Effort:** Low | **Priority:** P1 — High

### Problem

The system prompt is assembled from multiple dynamic sources: Wally persona, core behavior rules, intent-classified knowledge chunks (up to 63 .md files), site context, content style samples, and custom instructions. There is no enforcement to prevent the system prompt from consuming the majority of the model's context window.

> **Note:** Sonnet has a 200K token context window but effective reasoning degrades beyond ~30K tokens of input. If the system prompt alone is 8,000–15,000 tokens, plus 40 messages of history, you are regularly hitting degraded performance territory.

### Solution

Implement a token budget system in `PromptBuilderService` that allocates fixed maximums to each system prompt section, logs actual usage on every request, and enforces hard caps with graceful trimming.

---

### 3.1 Define Token Budget Constants (NestJS)

```typescript
// prompt-builder.service.ts
const TOKEN_BUDGET = {
  SYSTEM_TOTAL_MAX:    8000,   // hard cap on entire system prompt
  IDENTITY_RULES:       800,   // static persona + behavior rules
  KNOWLEDGE_CHUNKS:    2500,   // intent-classified .md files
  SITE_CONTEXT:        2000,   // WP version, plugins, theme, etc.
  ACTION_MEMORY:        400,   // recent actions log (Fix 1)
  CONTENT_STYLE:        600,   // recent post samples
  CUSTOM_INSTRUCTIONS:  300,   // wally_custom_prompt option
  HISTORY_MAX:         8000,   // conversation history (40 msgs)
  TOOL_DEFINITIONS:    3000,   // function/tool specs
  // Total request budget target: ~20,000 tokens
};
```

---

### 3.2 Token Counting Utility

```typescript
// token-counter.util.ts
export function estimateTokens(text: string): number {
  return Math.ceil(text.length / 4);  // conservative approximation
}

export function trimToTokenBudget(text: string, maxTokens: number): string {
  const maxChars = maxTokens * 4;
  if (text.length <= maxChars) return text;
  // Find last newline before the limit to avoid cutting mid-sentence
  const cutPoint = text.lastIndexOf('\n', maxChars);
  return text.slice(0, cutPoint > 0 ? cutPoint : maxChars) + '\n[...trimmed]';
}
```

---

### 3.3 Enforce Budgets in PromptBuilderService

```typescript
async buildSystemPrompt(context: ChatContext): Promise<string> {
  const sections: Record<string, string> = {};

  sections.identity  = this.buildIdentityBlock();  // static
  sections.knowledge = trimToTokenBudget(
    this.knowledgeLoader.load(context.intents),
    TOKEN_BUDGET.KNOWLEDGE_CHUNKS
  );
  sections.site      = trimToTokenBudget(
    this.buildSiteContextBlock(context.siteProfile),
    TOKEN_BUDGET.SITE_CONTEXT
  );
  sections.actions   = trimToTokenBudget(
    this.buildActionMemoryBlock(context.recentActions),
    TOKEN_BUDGET.ACTION_MEMORY
  );
  sections.style     = trimToTokenBudget(
    context.contentStyle ?? '',
    TOKEN_BUDGET.CONTENT_STYLE
  );
  sections.custom    = trimToTokenBudget(
    context.customInstructions ?? '',
    TOKEN_BUDGET.CUSTOM_INSTRUCTIONS
  );

  // Log token usage per section
  const usage = Object.entries(sections).map(([k, v]) =>
    `${k}: ~${estimateTokens(v)} tokens`
  );
  this.logger.debug('Prompt budget: ' + usage.join(' | '));

  const fullPrompt = Object.values(sections).filter(Boolean).join('\n\n');
  return trimToTokenBudget(fullPrompt, TOKEN_BUDGET.SYSTEM_TOTAL_MAX);
}
```

### Acceptance Criteria

- [ ] System prompt total never exceeds 8,000 tokens (verifiable in logs)
- [ ] Each section has a documented max and is trimmed before assembly
- [ ] Token usage is logged per-section on every request
- [ ] Trimming uses newline-aware cutting, never mid-sentence truncation
- [ ] Knowledge chunk injection is reduced first if total budget is exceeded

## Fix 5 — Intent Classifier Improvement

**Impact:** Medium | **Effort:** High | **Priority:** P2 — Medium

### Problem

The `IntentClassifierService` uses regex pattern matching on the user's message to determine which knowledge chunks to inject. Regex is brittle: it misses intent when users phrase things unexpectedly, and over-matches on unrelated text. The result is wrong knowledge being injected — or no knowledge at all.

> **Example failure modes:**
> - User asks "Can you remove the hello dolly thing?" — regex doesn't match `plugins` intent because it looks for `plugin/install/activate`
> - User asks "fix my SEO" — regex misses that this requires Yoast plugin knowledge

### Solution

Two phases. Phase A is a quick win (1–2 days). Phase B is the proper long-term fix (1 week).

---

### Phase A — Expand Regex Patterns (1–2 days)

Expand patterns with more synonyms and add an `ALWAYS_ON` set of knowledge files injected on every request regardless of intent:

```typescript
// intent-classifier.service.ts

// Always inject these regardless of detected intent (~500 tokens)
const ALWAYS_ON_KNOWLEDGE = [
  'wordpress-basics.md',
  'wally-capabilities.md',
  'confirmation-flows.md',
];

const INTENT_PATTERNS: Record<string, RegExp[]> = {
  plugins: [
    /plugin/i, /install/i, /activate/i, /deactivate/i, /extension/i,
    /addon/i, /add-on/i, /remove.*plugin/i, /get rid of/i,
    /yoast|akismet|woocommerce|elementor|jetpack/i,  // common plugin names
  ],
  content: [
    /post|page|article|blog/i, /content|copy|text/i,
    /title|heading|slug|excerpt/i, /publish|draft|schedule/i,
  ],
  elementor: [
    /elementor/i, /widget|section|column/i, /builder|visual/i,
    /layout|design|edit.*page/i,
  ],
  seo: [
    /seo|search engine/i, /meta|description|keyword/i,
    /rank|google|sitemap/i, /yoast|rankmath/i,
  ],
};
```

---

### Phase B — LLM-Based Intent Classification (1 week)

Replace regex with a fast Haiku call that classifies intent before the main chat request. Adds ~200ms latency but dramatically improves accuracy. The interface is identical (returns string array), so the swap is drop-in:

```typescript
// intent-classifier.service.ts
async classifyWithLLM(message: string, recentHistory: Message[]): Promise<string[]> {
  const response = await this.anthropic.messages.create({
    model: 'claude-haiku-4-5-20251001',
    max_tokens: 100,
    system: `You are an intent classifier for a WordPress admin assistant.
Classify the user message into one or more of these intents:
plugins, content, elementor, seo, settings, woocommerce, media, users, general.
Reply with ONLY a JSON array of intent strings, e.g. ["plugins", "content"].
If unsure, include "general".`,
    messages: [
      ...recentHistory.slice(-3).map(h => ({ role: h.role, content: h.content })),
      { role: 'user', content: message }
    ]
  });

  try {
    return JSON.parse(response.content[0].text);
  } catch {
    return ['general'];  // safe fallback
  }
}
```

> **Note:** Phase A should be implemented immediately — no architecture changes required. Phase B is a sprint task. Implement Phase A first, ship it, then do Phase B.

### Acceptance Criteria

**Phase A:**
- [ ] `ALWAYS_ON_KNOWLEDGE` files are injected on every request
- [ ] Common plugin name synonyms (Yoast, Akismet, etc.) trigger the `plugins` intent
- [ ] "get rid of", "remove", "delete" phrasing triggers relevant intents

**Phase B:**
- [ ] LLM classifier returns valid JSON array on 99%+ of requests
- [ ] Fallback to regex if LLM classifier call fails or times out (>500ms)
- [ ] Classification latency stays under 300ms

## What NOT to Change

The following parts of the current architecture are correct and should not be modified:

- Tool-use loop (up to 10 iterations) — this is the right pattern
- Stateless backend design — correct, scales well
- DB-persisted conversation history in `wp_wally_messages` — solid foundation
- Dynamic system prompt rebuilding per request — correct approach
- SSE streaming from backend to plugin to browser — good UX pattern
- License + rate-limit validation on every request — keep as-is
- Tool definitions structure (PHP classes with JSON schema) — well designed
